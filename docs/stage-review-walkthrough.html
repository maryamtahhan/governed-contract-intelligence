What you are looking at

the 30-second version

The page is a replay of one finished batch run of a contract-review pipeline over 19 real contracts from the CUAD test split. For each contract it shows the model's output for one classification step, four clause extractions, and one risk judgment, placed next to the expert annotation the scorer compared it against.

It is a replay, not a live service. Every card is rendered from results.json; the live button is disabled because the server was started without an endpoint. Clicking a document on the left replays its recorded stages at roughly the latency they actually took.

Say this early

This is example data, and view A measures model quality. It is the direct run: the batch runner called a bare vLLM endpoint, with no Praxis gateway, no label routing, and no audit trail. The comparison run adds the governance path — entry, label, pool, trace — but it is a failed run kept in the appendix, so it is not quality evidence. Gateway behaviour is also documented on the trace UI and in FINDINGS.md.

Start here: the words on the diagrams

plain language
WordWhat it actually is
Batch runnerThe Python command you start — hybrid-run --target direct or hybrid-run --target gateway (the older hybrid-direct-arm and hybrid-review commands are aliases). It reads documents, builds prompts, sends HTTP requests, parses replies and scores them. It runs on CPU and never serves a model. Older notes call this the “client” or “pipeline client”.
EndpointA running vLLM server. It exposes /v1/chat/completions and does the inference.
Entry (general / sensitive)Which door the request uses. The batch runner screens the document for personal data: clean documents go to the general entry (:8080); documents with personal data go to the sensitive entry (:8083), which fails closed instead of spilling to an unapproved pool.
Ingress relayThe trace-ui service at the entry. It writes the request into the audit trail and forwards it to praxis. It does not choose a pool or run a model.
PraxisThe policy gate. It reads the entry and picks a pool using the active routing config (all-gpu, gpu-small, round-robin or hybrid) — pinned policy, no classifier in the request path (removed 2026-11-05; the measured runs it recorded are described below). It does not run the model.
Pool relayThe second trace-ui hop. After praxis picks a pool, this relay records the actual model call and forwards it to that pool's vLLM server. It also does not run a model.
PoolA named destination such as vllm-cpu or vllm-gpu-approved. The name is a routing tier, not a promise about the hardware behind it; the deployment behind the name is what actually runs.
Routing configOne of four named policies over the same pools: all-gpu, gpu-small, round-robin or hybrid. The config name describes routing behavior, not hardware: read the pool map to see what actually answered. Praxis hot-swaps them without a restart, which is how the same stack was measured under each policy. The old word “arm” meant the same thing, and old run directories still contain arm-.

Keep two questions separate. Where are prompts built? Always in the batch runner, CPU-side. Where does inference run? At the endpoint for a direct run, or in the pool praxis chose for a through-stack run.

How a document is scored

five verdicts, one metric

Extraction is scored by containment, not span equality. A prediction is correct when either normalised string contains the other. A wider quote that includes the annotated text passes; a correct paraphrase fails. Every verdict badge maps to one scorer outcome:

VerdictMeaningView AAppendix B
matchThe model quoted the clause, and the quote matches the annotation under containment.206
absent — correctBoth the annotation and the model say there is no clause of this category.3816
not annotatedThe model quoted a clause where CUAD has none for this category — a scoring miss, not proof the words are absent from the contract.101
missedThe annotation has a clause; the model reported none.61
quote not matchedThe model answered, but its quote does not contain the annotation.20
no recordThe call failed (502/503/504), so there is no answer to score. It is not a correct absence, and the scorer no longer credits one.052
View A: 76 fields = 19 documents × 4 categories; 20 matches plus 38 correct absences = 58 of 76. View B: only 24 of 76 extract calls returned an answer, so 22 fields are correct and 52 have no record — its score is not comparable to view A.

Risk is separate. The model applies a rubric and returns a level with reasons. “Fully correct” means every scored field in that document passed. On this dataset that is the four clauses plus risk; the document type is not scored because the manifest has no type annotation.

What “ground truth” means here

three kinds of annotation, one answer key

Every badge on the page compares the model against ground truth — the CUAD annotations, short-handed to “truth”. It is worth being precise about that term, because it is not one thing and it is not a lawyer's opinion. All of it ships in data/cuad-test/ground_truth.json, derived from the CUAD expert annotations.

Ground truthWhere it comes fromWhat a match means
Clause annotation
clauses.*		 A CUAD annotator quoted the clause for that category in that contract, or labelled the category as having none. The model's quote and the annotation contain one another after normalisation. A correct paraphrase still fails.
Risk level
risk		 Not an annotator: pipeline/risk.py assess_risk() applied to the expert clauses by the converter that built the manifest. The model applied the same rule to the clauses it extracted. This is a rubric-following check, not a legal judgment.
Report expectations Computed at scoring time by evalkit/score.py report_checks() from the annotations: governing-law jurisdictions, the set of high-risk contracts. The report named a jurisdiction and a high-risk contract the annotations support. Nothing about the report is stored as a field in the dataset.

“No clause annotated” is not “no clause in the contract”. An empty category is a statement by CUAD for that category, but CUAD labels are not exhaustive: a contract can contain an audit right the annotators did not label. The badge says not annotated for that reason; it replaced an earlier wording, “clause not in contract”, that claimed more than the annotation does. Precision is therefore reported as a lower bound, as FINDINGS.md does.

Silence in the manifest can hide an explicit negative. CUAD's own records distinguish “no answer because there is no such clause” (is_impossible: true) from “no QA entry at all”; the converter stores both as null. Watchit Media's content-license agreement shows why the distinction matters: its only “terminat*” sentence is a cancellation-fee clause, CUAD explicitly marks “Termination For Convenience” impossible for it, and the model quoted that sentence. The quote is real text, but it prices what termination costs; it does not grant a termination right. So the model earns not annotated here, and the card's “✓ quote located in source” still stands.

A missing annotation is not an empty one. The classify card shows type: null for every document in this manifest. That means “nobody annotated the type”, so the field is skipped rather than scored wrong. The page keeps the two apart: null truth is unscored; a truth of “none” is scored and can be right or wrong.

Truth and source verification are two different checks

Every extract card runs two checks that look similar and answer different questions:

  • Verdict — does the model's answer agree with the annotation? This is what the score counts.
  • Verified in source — does the quoted string literally occur in the contract text? This is a whitespace-tolerant search of the file, independent of the annotation.

They can disagree in both directions, and the page shows both. A quote can match the annotation yet not occur verbatim, if the model spliced words from different sentences: CENTRACK's termination quote is scored correct and still does not appear in the source as a contiguous string. A quote can be verified yet scored wrong, if it is a real clause CUAD did not label: all ten false positives in this run are genuine strings in their contracts. Use the verdict for accuracy and the highlight for “is the model making this up”.

On a contract pasted in live there is no annotation, so every field is marked unscored: the quote is still located in the source, but no correctness is claimed and nothing is added to the meter. That is the honest reading of “there is no answer key for this one”.

Do not overclaim the routing

The classifier labelled 1,200 of 1,201 steps MEDIUM (complexity accuracy ≈ 0.001), and the ROSA overlay points the specialist's forward at the CPU MoE. Config D is therefore a CPU-first policy with the GPU reserved for cross-document synthesis: 600 extraction calls were answered by the CPU specialist, the remaining single-document calls were forwarded to the CPU MoE, and only the portfolio report reached the GPU. The 99.9% CPU-served share is the policy, not demonstrated semantic routing. The honest claim is governance and cost, not that the classifier separated simple from complex work. That measurement is also why the classifier was removed from the request path (2026-11-05): the routing it actually produced is now expressed directly as pinned policy.

Read it honestly

what a sharp reviewer will catch

These points are worth having ready before someone else finds them.

Must disclose

Risk is below the always-answer-“high” baseline. The page shows 0.632 against a 0.684 line. Do not hide the bar. The model predicts “high” 14 times against 13 annotated, but its swaps cost more than its hits: 2 high-risk contracts are called medium or low, and 3 non-high contracts are called high. That is the rubric-following weakness the project set out to measure. The baseline is on the page because hiding it would mislead.

Must disclose or fix

The report score on the page is 64.5%; the run's stored metrics.json says 26.3%. The scorer changed after this run was written: the governing-law comparison now reduces clauses to jurisdictions, and “highest risk” now accepts any annotated high-risk contract instead of one alphabetical pick. The page recomputes with the current scorer; the stored file is stale. Either re-score the run before presenting or say plainly that the page uses the current scorer.

Worth knowing

The report does not tally the risk cards. The direct runner builds the report prompt from the extract records, not the risk labels. It re-judges risk from the clauses and returned 4 high / 7 medium / 8 low, while the risk stage produced 14 / 1 / 4. Treat the report check as a second, independent judgment.

Worth knowing

“Fully correct” includes documents where the right answer was “no clause”. Five documents pass every field; two of them (Pcquote and MFA Financial) are 5/5 because all four categories were correctly absent and the risk level matched. That is a real result, but it is not the same difficulty as the fully correct document with three quoted clauses. Show both.

Worth knowing

The badge says “not annotated”, not “not in the contract”. The annotation says no clause was labelled for that category. CUAD annotations are not exhaustive, so a quote can be a real clause the annotators did not label, or a real sentence that does not grant the right the category names. The truth block says “No clause annotated for this category”, and the badge now says the same thing. Treat precision as a lower bound, as FINDINGS.md does.

Worth knowing

The pipeline strip says “parallel”, but this is a batch replay. The batch runner issues the four extracts one after another; the interactive path is what fans them out. The recorded data has per-step latency, not overlap, so the replay cannot prove concurrency. Do not claim the fan-out from this page.

Worth knowing

The page folds one repeated doc_id. CUAD's manifest lists 20 entries for 19 unique contracts, and the batch runner executed all 20 — 121 steps, not 115. The page shows the first pass and scores the document once, so its counts (76 extract fields, 115 calls) are four fields and six steps smaller than the run's own summary.json. The header chip says “1 repeated doc_id folded” so the difference is stated rather than discovered.

Questions to expect

short answers
What does “direct run” mean?
A configuration is one run in the experiment: the same documents, prompts, parser and scorer, with one variable changed. Direct means the batch runner called one vLLM endpoint straight (http://localhost:8000/v1) — no trace-ui relay, no praxis gateway, no label routing, no PII entry, no audit trail. That isolates model quality from the stack: everything on view A is the model, and its cards carry no route, label or trace chip because no gateway was there to name one. The trade is that it proves nothing about governance; the through-stack runs and the appendix comparison run exist for that.
Where is the gateway and the routing?
Not on view A. It is the direct run: the pipeline called vLLM directly, so there are no labels, no routing decisions, and no audit records. The appendix comparison run shows the gateway path; the full audit trail is on the trace UI. Mixing the two surfaces is the easiest way to overclaim.
Is this one model, or one per stage?
View A is one model for every stage: Qwen3.5-35B-A3B answers classify, all four extracts, risk and the report. The broken-down design is measured elsewhere. The specialist composite answers extraction with a fine-tuned RoBERTa-large QA encoder — full-document F1 0.780, top-5 retrieval F1 0.800, recall 1.000, and it cannot invent a quote because it returns spans of the input — against 0.712 for the generative MoE on the same held-out test split and the same 80 fields, and it forwards classify, risk and report to a general model. That is a local direct run (runs/retrieval/e2e-specialist.json), not a through-stack run. The appendix comparison run is the through-stack path, and it is contaminated by infrastructure failures, so it shows routing, not that quality.
Didn't the specialist perform better?
On extraction, yes — that is the measured result, and it is the reason the broken-down pipeline is worth pursuing. The through-stack run failing is a separate fact.
So why isn't the appendix run the better configuration?
Because a quality measurement and a working through-stack run are different things. The specialist's extraction result is real — 0.780 full document, 0.800 at top-5, against 0.712 for the generative MoE — but it came from a local direct run, where every extraction prompt was answered. Through the gateway the same work has to survive labelling, pool health and the network, and this run did not: 82 of 121 calls failed, 14 of them at the router's ~30 s timeout. The architecture claim stands; the end-to-end number does not exist yet. Re-run at lower concurrency with the router timeout raised.
Why does the compare run show vllm-cpu?
Because praxis chose the pool named vllm-cpu. Pool names are routing tiers inherited from the llm-d convention, not hardware: in the example run every pool was CPU-served, so a vllm-gpu chip does not by itself mean a GPU answered. The model chip on view A (example host · 4× A10G) is the only hardware claim on the page, and it belongs to the direct run.
Can the gateway tell me which endpoint answered?
The pool, not the endpoint. A trace record holds the route name, label, entry, hops and health checks; the pool's upstream URL and Deployment are configuration, and the database stores neither per request. To say “this call ran on cpureal-vllm-gpu-approved” you would read that pool's deployment and trust that no rollout moved it since.
Which checkpoint actually answered a call?
Ask the response body. Each card's model chip comes from the body's model field, which is why a specialist pool can name cuad-specialist while a forwarded prompt names the alias. View B records this per call and lists the models with counts; view A predates that capture, so it has only the run-level checkpoint label. A run without the field cannot be backfilled — re-running is the fix.
Why is precision only 0.625?
Ten false positives and two unmatched quotes. Some of those are annotation gaps rather than model errors, because CUAD labels are not exhaustive. The project treats reported precision as a lower bound for every model, and every run is scored on the same annotations.
What does “absent — correct” mean?
The annotation has no clause for that category and the model also reported none. It is a correct answer, and it is 38 of the 76 fields here. It matters because a model that says “no clause” everywhere would score well on those fields and badly on recall.
Why 19 documents when the document says 20?
The manifest lists 20 entries but one doc_id is repeated, so the runner executed that contract twice — 121 steps across 20 entries. The page keeps the first pass and shows 19 cards, and the header chip says “1 repeated doc_id folded”. Its counts are therefore four fields smaller than the run's summary.json; the alternative was to score one contract against two cards.
Why is the classify card not scored?
The CUAD manifest has type: null for these documents. The card still shows the model's prediction (“NDA”, term, reference), but there is no truth to compare, so it contributes no field and type accuracy is null. The page's own help text says type counts toward “fully correct”; on this dataset it does not.
What exactly is “truth” on this page?
The CUAD expert annotations, not a lawyer's opinion and not another model. Clause truth is an annotated quote or an explicit “none”. Risk truth is the project's own rubric applied to those expert clauses, so the risk field checks rubric-following. The report's expectations are computed from the annotations at scoring time. See What “truth” means here for the three kinds and the difference between a verdict and a source check.
Is the model inventing quotes?
Two extract cards are marked “quote not matched”, and ten are false positives against the annotation. Every card also runs a separate source check and shows where the quote occurs. A quote that is not in the file would be visible there. The useful distinction is between “not in the contract” and “not what the annotator labelled”.
Why are the latencies in seconds?
GPU-served MoE calls on batch prompts. Medians are 2–4 s per extraction. The workload is batch contract review, so the pitch is throughput and GPU-time reduction, not interactive response.
Risk is below the baseline. Is that a bug?
No. It is the measurement. The risk stage predicts “high” 14 times against 13 annotated, but it never gets a medium right and swaps two high-risk contracts down to medium or low. That is enough to land below the constant answer, and the baseline line makes it visible instead of letting 0.632 look respectable.
Can I run a contract I paste in?
Yes, when the server was started with --endpoint. The composer accepts one pasted contract, several text files, or a .zip/.tar.gz of them; a batch keeps two documents in flight and streams each stage as it lands. Submitted documents are unscored — there is no annotation — but every quote is still located in the source. Archives are read in memory, member paths cannot escape the archive, and binary members are skipped and named, not fed to the model. PDF/DOCX ingestion is not built. A live submission is a direct run: the same prompt builders and scorer shape as the batch runner, but sent straight to the endpoint — no relay, no praxis label, no PII entry, no sensitive-pool routing — so it does not exercise the governance the through-stack runs show. To run fresh documents through the governed path, use hybrid-run --target gateway and replay that run directory.
Where did the pool load and throughput numbers go?
They moved to /monitor, so the stage panel stays readable. Device-seconds per pool and the vLLM bench sweep at concurrency 1, 4 and 16 are one click from the header. The sweep is the only place the page compares hardware directly: on the CUAD prompts, output throughput goes from 14.7 to 78.4 tokens/s on CPU and from 92.7 to 226 tokens/s on GPU between c1 and c16. They are not stage latencies from either view.
Why does the report tile disagree with metrics.json?
The scorer was revised after the run. The page recomputes from results.json with the current code; metrics.json keeps the number from the scorer version used at run time. Re-score the run or disclose the difference.

Appendix — the failed A/B comparison run

This comparison run is kept as an appendix because 82 of its 121 calls failed. It is evidence of the gateway path — entry, label, pool, trace — not of model quality. The main guide stops before it.

A/B order is set by the server, not by this table

The CUAD example below was started with A = direct run (arm-direct-moe-gpu-v2) and B = gateway run (arm-D-specialist). The default make dashboard-up uses the opposite order: A = ROSA praxis run (runs/rosa-200/hybrid) and B = direct GPU run (runs/direct/gpu-moe). The two paths, drawn

View A — direct run. The batch runner talks to the model endpoint; there is nothing else in the path.

No relay, no praxis, no label, no pool choice, no trace id. The batch runner only builds prompts and parses responses — direct.py imports the same builders from review.py as the through-stack runner. Every model call — classify, extract ×4, risk — goes to this one endpoint, so the endpoint's hardware (CPU or GPU) answers all stages. The response carries no routing headers, which is why the cards show no entry, label or pool chips — not because the page failed to render them.

The batch runner is CPU-side orchestration; classify, extract ×4 and risk are model calls that land in the pool praxis chose, plus one report call at the end of the run. The response echoes x-demo-entry, x-demo-classification, x-demo-route and x-praxis-trace-id. The relays record the route name and hop timings — not the pod or upstream URL.

Why measure both? They are not competing for the same score. The direct run sets the model-quality reference with nothing in the path; the through-stack runs show what the gateway does to a request. The controlled comparison is the same weights on CPU and GPU: the two direct runs agree exactly on quality — F1 0.690, risk 0.632, 5/19 fully correct on both — and differ on latency, where CPU classify took 3.4–21.3 s against ~0.6–1 s on four A10Gs. Quality did not change; speed did.

Pool names are tiers, not hardware

The pool names come from the llm-d routing convention: vllm-gpu, vllm-gpu-approved, vllm-cpu, vllm-gpu-small. In the comparison run behind this appendix, every one of those pools was served on CPU: the pre-ROSA deployment ran the 7B checkpoint on the two “gpu” pools and the 1.5B on vllm-cpu, all under the single alias Semantic-Qwen. So a route chip reading vllm-cpu names the pool praxis chose; it does not by itself say what silicon answered. The only GPU-served view on this page is A — and its cards carry no route chip at all, because a direct call has no gateway to name one.

On a GPU-bearing cluster this changes. deploy/openshift/gpu-moe stacks on cpu-real-moe and points the two expensive names — vllm-gpu and vllm-gpu-approved — at a 4×A10G deployment of the same 35B-A3B checkpoint, leaving vllm-cpu on CPU. Then a vllm-gpu chip really does mean a GPU, and the CPU/GPU contrast becomes one checkpoint on two hardwares rather than two different tiers. The claim to make is the one measured: same quality, different latency.

Say this before toggling to B

The comparison run is a failed run, not a quality result. 82 of its 121 calls returned 502, 503 or 504 at concurrency 12, so only 39 answers exist: most of its cards read “no record”. The cause was infrastructure — the tunnel and cluster failures recorded in FINDINGS.md §9 — not the specialist model. Do not let “few answers” read as “the specialist performs badly”: extraction was measured separately, and it did better than the generative model.

The specialist did measure better — on extraction, off the stack

On the held-out test split, with the same scorer and the same 80 extract fields as the recorded MoE configuration, the CUAD specialist answered with F1 0.780 full-document (P 0.657, R 0.958) and F1 0.800 when fed litil's top-5 retrieved chunks (P 0.667, R 1.000), against 0.712 for the generative MoE. Recall is 1.000 at top-5, so no annotated clause was missed, and the encoder returns spans of the input — it cannot invent a quote. The 12 remaining errors are extra spans, eight of them on text CUAD never annotated. Evidence: runs/retrieval/e2e-specialist.json and e2e-specialist-top10.json. This was a local direct run, not through the stack: that is the measurement the broken-down-pipeline argument rests on, and the reason view B's failed run is worth re-running rather than dismissing.

The gateway path, as the response reports it

entry → label → pool → trace

On view B the batch runner talks to the trace-ui ingress relay, which forwards to praxis. Praxis labels the request and chooses a pool; a second trace-ui relay then records the actual model call and forwards it to that pool. The response carries headers the pipeline stores on the record, and the chips on each classify, extract and risk card are rendered from those headers:

HeaderCard chipWhat it saysWhat it does not say
x-demo-entryentry generalWhich listener admitted the request. The PII screen sends sensitive documents through the sensitive entry — the one that fails closed.Which model ran.
x-demo-classificationlabel MEDIUMThe label praxis applied: SIMPLE, MEDIUM, COMPLEX or REASONING.Not the complexity annotation the run is scored against; the page shows that separately in the truth block.
x-demo-routepool vllm-cpuThe pool that answered.Not the pod, Service or upstream URL. The trace database stores the route name, classification, entry, hops and health checks — no endpoint identity. Pool → Deployment is configuration (TRACE_POOLS and *_UPSTREAM), not per-request evidence.
x-praxis-trace-idtrace …The id that ties the request to its hops and health checks in the trace UI.Whether the answer was any good.
x-praxis-fallbackrecord fieldWhether the named pool was the first choice or a fallback.Why the first choice failed — that is in the hop record.

The rule praxis applies. SIMPLE and MEDIUM go to the CPU-side pools; COMPLEX and REASONING go to the GPU-side pools. On the sensitive entry a REASONING request fails closed with an explicit 502 rather than degrading to CPU; on the general entry it degrades to CPU with the fallback signal set. View B recorded COMPLEX ×3 and MEDIUM ×6 — only the calls that succeeded carry a label at all, because a failed call returns no headers to read.

Model identity is per call, and new

Cards also carry a model chip, read from the model field of each response body — not from praxis. That is the only per-call evidence of which checkpoint answered: the gateway records the pool, a specialist pool names its own id (cuad-specialist), and a forwarded prompt returns the alias (Semantic-Qwen). Capture was added after view A was recorded, so view A has only the run-level checkpoint label; view B records it per call, and its routing panel and path strip list the models with counts. A run without the field cannot be backfilled; the deployment YAML names the checkpoints a pool could have run, but not which one answered a given call.

Must disclose if you show this run

A failed call is not a correct absence. The scorer used to credit a 502/503/504 on an annotated-absent clause as “correct absent”. On this comparison run that inflated extraction from 22 to 53 correct fields and reported one fully-correct document where none is. The page always showed those calls as no record; the scorer now agrees. If you quote a number from an older metrics.json, it may predate the fix.
